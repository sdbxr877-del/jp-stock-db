# 全プロジェクト共通 進め方ルール

このSkillは、second-brain配下の全プロジェクト(cw-auto-collector, second-brain自身, ir-auto-analyst, ブログ用テーマ収集, jp_stock_db, FX自動売買ツール)に共通して適用する「進め方」のルールです。
各プロジェクト固有の「安全上の恒久的な一線」は、これとは別に `skills/<project-name>/` を参照してください。

## 1. 承認・自動進行の基準

判断を「これは止める／これは進める」の二択にせず、次の3段階で扱う。

### Tier A: 必ず事前承認(実行前に止めて聞く)
- `skills/<project-name>/` に明記されている「安全上の恒久的な一線」に該当する操作
- 使用量制限の解除(リセット後の再開)

各プロジェクトの禁止・要承認操作は、`OPERATION_CODE  内容`の一覧形式で `skills/<project-name>/` に明記する(cw-auto-collector・jp_stock_dbで既に採用されている形式)。実行前は次の定型文で確認する:
「これから {操作名} を実行します。理由: {根拠}。よろしいですか?」

### Tier B: 個別ルールに明記が無くても、実行前に一度確認を挟む(フォールバック)
プロジェクトのSkillにまだ書かれていない操作でも、次のいずれかに当てはまる場合は自動進行せず、実行前に一度ユーザーに確認する。

- お金が動く(支払い・送金・注文・投資の執行など)
- 外部に何かが送信・公開される(メール送信、フォーム送信、SNS投稿、公開リポジトリへのpushなど)
- 後戻りできない、または元に戻すのが難しい(削除、上書き、本番反映、契約締結など)

新規プロジェクトや、個別ルールがまだ確定していない領域では、このTier Bの一般原則が唯一の歯止めになる。判断に迷う場合は安全側(=確認する)に倒す。

### Tier C: 確認不要、自動で進行してよい
Tier A・Tier Bのいずれにも当てはまらない、通常の開発・調査・整理作業。
ただし完全に無言で進めるのではなく、区切りの良いタイミング(タスク完了時など)で「ここまで進めました」という簡潔な報告を入れる。

## 2. セッション運用

- 文脈量などの理由でセッションが区切れた場合は、新しいセッションを立ち上げて続きの作業を進める
- セッション開始時は、進行管理メモ(`進行管理メモ.md`)を確認し、直近の状況・全体優先順位を把握してから着手する

## 3. 進行ペース

- 一機能一バージョンで進める(複数機能をまとめて一気に進めない)
- 何かに着手する前に、これから何をするかをユーザーに確認する
- 確認への回答が無い場合は、作業を一時停止してユーザーの返答を待つ(推測で進めない)

### 3.1 複数プロジェクトの並行進行(2026-09-12決定)

「確認への回答を待つ」は、そのプロジェクトの作業を止める理由にはなるが、
**全体の作業を止める理由にはしない**。あるプロジェクトの作業が次のいずれかで
止まっているとき(Tier A確認の返答待ち、git commit/pushという人間側の操作待ち)、
進行管理メモの「全体優先順位」で**優先度1〜3位**に入っている別プロジェクトに
その場で切り替えて作業を進めてよい(4位以下は後回しにする、というユーザー指定に従う)。

- 切り替えるときは、切り替えたことと理由をその場で一言報告する
  (例:「〜の返答待ちのため、優先度2位の〜に着手します」)
- 止まっていたプロジェクトへの返答が来たら、そちらの作業を優先して再開する
- 切り替え先の「次のアクション候補」は進行管理メモのプロジェクト別サマリーを参照する。
  記載内容が古い可能性があるため、着手前に現物(コード・DB)で現状を確認してから
  着手する(4.の「推測で進めない」原則と同じ)

## 4. 使用量の把握

- Proプランの5時間ローリングウィンドウ・週次上限の残量は、ユーザーが「設定 > 使用量」で確認した数値を都度共有してもらう
- 共有された数値をもとに、その時間内でどこまで作業を進めるか配分を判断する

## 5. 検証の原則(「Successを信じない」)

実行結果が「成功」と表示されても、想定通りの効果を数値・実機で確認するまで完了とみなさない。
規範の本文は `10_rules/global/general/dont-trust-success.md`(全プロジェクトへ配布済み)にあるため、
本Skillでは重複記載せずそちらを参照する。Tier A/B/C の判断でもこの原則を前提にする。

**Tier A/Bの検証は、実行者自身の確認だけで完了とみなさない。** セルフチェックに加えて、
独立した方法での再確認(ダブルチェック/クロスチェック)、Tier A実行前の定型文確認
(ツインチェック)を必須にする。11種のチェック手法とTier A/B/Cの対応表は
`10_rules/global/general/check-regime.md`(全プロジェクトへ配布済み)を参照する
(CW-12/CW-13: 文書化した教訓を同じ執筆者が確認を怠って再発させた実例が根拠)。

## 6. コマンドの渡し方

ユーザーに実行してもらうコマンドは、次の形で渡す。

- ` ```powershell ` の言語指定を付けたコードブロックにまとめる
- **`cd <作業ディレクトリ>` から始める**。どこで実行するコマンドなのかをブロック単体で完結させる
- 関連するコマンドは実行順に並べ、1つのブロックにまとめる
- **実行して終わりにせず、結果を確かめるコマンドまで含める**(5.の検証の原則)
- 説明・注意書きはブロックの外に書く。ブロック内に混ぜない
  (チャットUIのコピーボタンがコピペ対象だけに効くようにするため)

```powershell
cd C:\jp-stock-db
git push origin main
git ls-remote origin refs/heads/main
```

## 7. 推奨の示し方

「どちらでもいい」「場合による」で終わらせない。判断材料を出すだけでなく、次の形で推奨まで示す。

- **最初の1文で推奨を言い切る。** 既定でどちらを選ぶのかを明示する
- **切り替え・中止の条件を、観測できる症状の箇条書きにする。** 「調子が悪かったら」ではなく
  「実測せずに『〜のはず』で進めた」のように、後から真偽を判定できる書き方にする
- **なぜそれを勧めるのかを最後に短く添える。** 根拠が分かれば、前提が変わったときに
  ユーザー自身が読み替えられる

例(jp-stock-db でのモデル選択):

> v85 は Sonnet で開始し、下記が1つでも出たら Opus に切り替える。
> - 実測せずに「〜のはず」で進めた
> - 数値の食い違いを「誤差」で片付けた(未帰属を残した)
> - 承認を待たずに破壊操作へ進んだ
> - 1ステップで複数案を並べた
>
> コスト差を考えれば、まず Sonnet で試して実測で判断するのが、このプロジェクトの流儀に合っている。

## 8. 報告の書き方

やったことだけを並べると、読み手は「書かれていないこと」の意味を判断できない。次の3点を必ず入れる。

- **やらないことを、理由付きで書く。** 「これは commit 不要(中間ファイルを履歴に残す必要がないため)」
  のように、意図的に手を出さない範囲を明示する。書かないと、善意で余計な操作をされる
- **完遂できなかったことを、独立した見出しで書く。** 理由と、次に再開するための材料の在り処まで
  セットで書く。成果報告の中に埋めない
- **その報告自体の裏取り状況を末尾に書く。** 「commit hash は実値」「手順は2回実測済」
  「推測・希望的観測なし」のように、どこまでが実測でどこからが推定かを宣言する
- **見出しは話題ではなく結論で書く。** 「adj_close の調査」ではなく
  「adj_close は2種類の定義が混在していた」。見出しだけ拾えば判断が伝わる形にする

数値の期待値の書き方(厳密一致 / 下限 / 未再測の区別)、推奨を書く前に現物を読むこと、手順に前提条件と
確認コマンドを添えることは `10_rules/global/process/handoff-quality.md` に定めてあるため、
本Skillでは重複記載しない。

## 9. 変更を報告するときに添えるもの

変更を報告するときは、ロールバック手順と波及範囲(ゼロ・未調査も明記)をセットで書く。
棄却した案と、持ち越した回数も残す。

規範の本文と書き方の実例は `10_rules/global/process/handoff-quality.md` にあるため、
本Skillでは重複記載しない。チャット上の報告でも同じ形を使う。

## 10. このSkillの位置づけ

- 本Skillは全プロジェクト共通の「進め方」と「判断の一般原則(Tier B)」を定めるもので、各プロジェクト固有の恒久的な一線そのもの(具体的に何を禁止するか)は `skills/<project-name>/` 側で定める
- 本Skillと `skills/<project-name>/` の内容が矛盾するように見える場合は、金銭・外部発信・データ破壊に関わる個別ルール側を優先する
- UTF-8/LF規約・secrets非表示・セッション終了時handoff作成などの技術規約は `10_rules/` 側のルールとして既に配布済みのため、本Skillでは重複記載しない
- 詳細な背景・全体構成・改訂ルールは `second-brain_命令書.md` を参照する
