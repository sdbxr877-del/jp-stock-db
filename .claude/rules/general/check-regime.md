## 規範

ルールは文書化しただけでは守られない。**CW-12（.bat内の日本語コメント問題）は
文書化された翌々日以内に、同じ執筆者（Claude）自身の手で CW-13 として再発した。**
教訓を「覚えておく」ことは再発防止策として機能しない、という実例である。

したがって、チェックは「気をつける」という精神論ではなく、次のどちらかに
**翻訳できて初めて実効性を持つ**、という前提に立つ。

1. 破ったら先に進めなくなる仕組み（機械的ゲート・pre-commitフック）にする
2. 実行者自身とは構造的に独立した第三者（人間・別セッション・別エージェント）
   による確認を、手順として必須にする

以下は `チェック体制項目リスト`（ユーザー提供、2026-09-12）にある11種の
チェック手法を、本vaultの Tier A/B/C モデル（`skills/common/SKILL.md` §1）・
「Successを信じない」原則（[[general-dont-trust-success]]）にどう対応させるかの
対応表。

## 体制別（誰が・何人で確認するか）

| チェック種別 | 定義 | このvaultでの対応 |
|---|---|---|
| セルフチェック | 本人が確認。時間を置くと精度が上がる | Tier C全般の既定。変更直後に `gates.py` 相当の実行＋差分の読み直しを行う |
| ワンタイムチェック | あえて1人だけで集中。「誰かが直すだろう」という甘えを防ぐ | 「一機能一バージョン」原則（`skills/common/SKILL.md` §3）そのもの。複数を同時に進めないことが、責任の所在を1点に保つ |
| ダブルチェック | 1人目の成果物を別の人がもう一度確認する | Tier A/B操作は、実行者自身の確認（自スクリプトの終了コード等）**だけで完了とみなさない**。必ずもう1つ、独立した方法で再確認する（例: 登録スクリプト自身の判定に加え、`schtasks /Query` を別途手で叩く） |
| トリプルチェック | 作成者→一次確認者→最終承認者の3段階 | 現状は人員が2者（ユーザー・Claude）のため未導入。部署が増える段階になったら、不可逆性が最も高い操作（本番DB削除・実金送金等）に限定して導入を検討する（今は不要） |
| ツインチェック | 2人がその場で同時に同じ対象を確認する（指差呼称） | Tier Aの実行前確認定型文「これから{操作}を実行します。理由:{根拠}。よろしいですか?」がこれに当たる。Claudeが宣言し、ユーザーがその場で応答する、という指差呼称と同じ構造。**これは既に運用されているが、「ツインチェックである」と明示されていなかった** |
| ピアレビュー | 対等な同僚同士が検証し合う（上下関係なし） | 現状の人員（1名+Claude）では成立しない。近似策: 高リスクな変更では、経緯を伝えないレビュー専用のサブエージェント（Agent/Taskツール）に成果物だけを見せて独立評価させる |

## アプローチ別（どう確認するか）

| チェック種別 | 定義 | このvaultでの対応 |
|---|---|---|
| クロスチェック | 複数の異なる方法・データ源を突き合わせる | Tier A/B操作の検証は、必ず2つ以上の独立した情報源で行う（例: 登録スクリプトの標準出力 + 別途実行したOSコマンドの出力） |
| ファクトチェック | 情報の裏を一次情報でとる | handoff・進行管理メモ等の記述を鵜呑みにせず、実ファイル・実DBを直接読んで確認する（second-brain命令書§9のチェック漏れを2026-09-12に発見した手法そのもの） |
| エビデンスチェック | 数字と証憑を1件ずつ突き合わせる | 件数・金額などの主張には、算出根拠のクエリ・ログを添えて示す（`skills/common/SKILL.md` §8「報告の書き方」の裏取り状況の項目と同義） |
| リバースチェック | 成果物から逆算して確認する | 失敗記録テンプレート（`_templates/template-failure.md`）の「真因」欄そのもの。症状から遡って根本原因を特定する作業を指す |
| システムチェック | ツール・AIによる自動判定 | **最優先で投資する対象。** 人が都度気をつけるより先に、`gates.py` のような機械的ゲートに落とし込む。CW-13で追加した `G-BAT`（.batのASCII強制）がこの実例 |

## 結論: 3つの問いへの回答

**Q1. どうすれば全プロジェクト・全メンバーが同じように守れるか**
ルールは `10_rules/global/` に1回書き、`sync_rules.py --check`→`--apply` で
全プロジェクトへ機械的に配布する。各プロジェクトが個別に「真似る」のではなく、
配布の仕組み自体が同一性を保証する。skillsの `sync_skills.py` も同じ構造。

**Q2. どうすれば自分（Claude）が同じ過ちを自分で抑制できるか**
「気をつける」を信頼しない。再発防止策は原則として上表の「システムチェック」
（機械的ゲート）に翻訳する。機械化できないものだけ、セルフチェックの
チェックリストに追記するが、これは最終手段であり主策にはしない。

**Q3. どのようなルールなら絶対的に守れるか**
破ったら物理的に先へ進めなくなるルールだけが「絶対」になり得る
（`gates.py` がFAILしたらcommitしない、pre-commitフックが強制する）。
文書だけのルールは、CW-13が示すとおり、書いた本人にすら破られる。

## 関連過去教訓

  確認の手間を惜しんで同じ執筆者が同じミス（CW-13）を繰り返した実例。

  への翻訳が実際に有効だった実例として、本ルールの根拠になっている。
